# ベンダーの判定方法

請求書PDFから、どのベンダー・どの契約の請求かを特定する手順。

**具体的な判定条件と入力値はこのファイルに持たない。** 利用中のサービスや契約内容は組織固有の情報のため、`vendors.local.md`（リポジトリ管理外）に置く。

## 判定に使う手がかり

優先度の高い順。

| 手がかり | 内容 | 信頼度 |
|---|---|---|
| 適格請求書番号 | `T` + 13桁。請求元の法人を一意に特定できる | 高 |
| 請求書番号・顧客コード | 8桁程度の英数字。決済代行を挟む場合に商材を見分ける鍵になる | 中 |
| 本文の特徴文字列 | 法人名、サービス名、管理画面のドメインなど | 中 |
| ファイル名のパターン | 接頭辞（`Invoice-` など）。ベンダーごとに規則がある | 低 |

適格請求書番号は国税庁の適格請求書発行事業者公表サイトで照会できる。番号から法人名が判明するため、番号だけで判定できるベンダーも多い。

**番号だけでは足りないケース**があることに注意する。

- 決済代行サービスを挟むと、請求元は同じでも中身の商材が異なる
- 同じ法人でも、契約プランや契約ドメインごとに別の明細になる

この場合は、番号に加えて本文の特徴文字列で契約単位まで絞り込む。

## 判定の順序

**判定条件は重複しうる。** 例えばファイル名の接頭辞は複数のベンダーで共通することがある。

そのため対応表には**確認する順序**を持たせ、**最初に条件を満たしたものを採用する**。条件がより厳しい（複数条件のAND）ベンダーを先に置くと誤判定が起きにくい。

新しいベンダーを追加する際は、既存の判定条件と重複しないか必ず確認する。重複すると、どちらに解決されるかが順序依存になり、後から追加した側が永久に選ばれなくなる事故が起きる。

## 同一請求元で複数契約があるケース

次のパターンがある。いずれも**契約単位まで特定してから**入力値を引く。

| パターン | 見分け方 |
|---|---|
| 決済代行経由 | 請求書番号や本文の商材名で判別する |
| 契約ドメイン別 | 本文に記載されたドメインで判別する |
| 契約プラン別 | 本文の商品名・プラン名で判別する |

## 必要な入力値

ベンダーと契約を特定したら、次の3つを決める。

| 項目 | 内容 | 用途 |
|---|---|---|
| カード利用名 | カード会社が付与する加盟店名 | 明細一覧で対象行を絞り込む |
| 稟議名 | 紐付ける購買申請の件名（原則は明細行の「購買申請」。「関連申請」欄は使わない） | 稟議の検索 |
| 内訳 | 費目の分類 | フォームの内訳欄 |

いずれも組織ごとに異なるため、このリポジトリには持たない。

## vendors.local.md の書式

このファイルと同じ `references/` 配下に `vendors.local.md` を作成する。`.gitignore` 済みのためコミットされない。

```markdown
## 判定の順序

（条件が厳しいものから順に列挙する）

## 判定表

| 順 | ベンダー・契約 | 判定条件 | カード利用名 | 稟議名 | 内訳 |
|---|---|---|---|---|---|
| 1 | （契約単位で1行） | （番号・本文・ファイル名の組み合わせ） | | | |
```

判定条件の書き方の例:

- `T` + 13桁の番号のみで確定するもの
- 番号 + 本文に特定の文字列が含まれること
- ファイル名が特定の接頭辞で始まること + 番号
- 番号は共通で、本文の商材名で分岐するもの

## 対応表が無い場合

`vendors.local.md` が存在しない場合は、**推測で入力しない。**

1. PDFから読み取った適格請求書番号・金額・特徴的な文字列を利用者に提示する
2. どのベンダー・どの契約かを確認する
3. カード利用名・稟議名・内訳を尋ねる
4. 判明した内容を `vendors.local.md` に追記するか、利用者に追記を促す

金額や稟議を誤ると、経費申請として誤った内容が承認フローに乗る。曖昧なまま進めない。
