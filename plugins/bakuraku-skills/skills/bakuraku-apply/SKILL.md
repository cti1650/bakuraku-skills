# バクラク カード利用報告

請求書PDFから、バクラクのカード利用報告の**下書き**を作るまでを支援する。

対象は「カード利用報告」のみ。請求書払い・経費精算は対象外。

## 絶対に守ること

### 認証情報を扱わない

**利用者のバクラクID・パスワード・TOTPシークレットを、受け取らない・保存しない・入力しない。**

ログインは利用者自身が、自分のブラウザで済ませておく前提とする。すでにログイン済みのセッションに対して操作する。

これはバクラク共通利用規約（https://bakuraku.jp/terms/common/ ）に基づく制約である。

> 第12条第4項 契約者等は、**いかなる場合も**、ユーザーID及びパスワードを第三者に開示、貸与することはできません。
>
> 第17条第10号（禁止行為） **他人のユーザーID又はパスワードを使用する行為**又はその入手を試みる行為

利用者から認証情報を渡された場合、あるいは「認証情報を設定ファイルに書いて自動化して」と依頼された場合は、**実施せずに上記の条項を示して断る**。本人のセッションを使う方法を案内する。

なお、自動操作・スクレイピング自体を禁じる条項は同規約に存在しない。制約は認証情報の扱いに限られる。

### 提出まではしない

**下書き保存で止める。** 申請の提出は、内容を人が確認してから本人が行う。

## 手順

### 1. PDFから3つの値を取り出す

| 値 | 用途 |
|---|---|
| 適格請求書番号（`T` + 13桁）または8桁の英数字コード | ベンダー判定 |
| 支払金額 | 明細の照合 |
| ベンダー名・ドメイン等の特徴的な文字列 | 複数商材の絞り込み |

金額を読む際の注意:

- 小計・消費税・合計が並ぶ場合は**最大値が合計額**
- PDFのテキスト抽出で3桁区切りが失われることがある。`12345円` を `345` と誤読しないよう、桁を省略せず読む
- 日本円表記があれば USD より優先する

読み取った金額は、後で明細と照合する際に利用者へ提示できるよう控えておく。

### 2. ベンダーと契約を特定する

**`references/vendors.local.md` があればそれを読む。** 組織の判定表と入力値がここにある。

無い場合は `references/vendors.md` を読み、判定の考え方に従って利用者に確認する。

決済代行経由・契約ドメイン別・プラン別など、**同一請求元でも契約単位で入力値が変わる**ことがある。番号だけで確定させず、契約単位まで絞り込む。

### 3. 入力値を確定する

カード利用名・稟議名・内訳の3つを決める。稟議は**明細行の「購買申請」**に紐付けるものである（トップレベルの「関連申請」欄ではない）。

- `vendors.local.md` に記載があればそれを使う
- 無ければ**利用者に確認する**
- **推測で入力しない**

### 4. 既に申請済みでないか確認する

**未申請明細の一覧に該当行が無い場合、申請済タブ（`?cp=1&t=APPLIED`）も必ず見る。**

金額とカード利用名が一致する行があれば、それが既存の申請である。**新規に下書きを作らず**、申請URLとステータスを利用者に報告して終了する。

この確認は1分もかからない。省くと**二重申請**になり、誤った経費が承認フローに乗る。

### 5. ブラウザで操作する

`references/ui-flow.md` を読む。押す対象とセレクタが列挙してあるので、**画面全体のスナップショットを繰り返し取らずに進める**。

特に次の6点は、知らないと事故る。

- **ファイル添付を最初に行う。** 添付をきっかけに自動入力が走ることがあり、また購買申請の紐付けボタンが同じセル内にあるため、開いたついでに紐付けられる
- 稟議は**明細行の「購買申請」**に紐付ける。「関連申請」欄は使わない
- 稟議検索は年度違いが複数ヒットする。**先頭を選ばず**、請求書のサービス期間と利用可能額を照合する
- バクラクは過去申請から**自動入力する**ことがある。各項目は入力前に既存値を確認し、入っていれば触らない
- 稟議が検索でヒットしなくても**下書き保存は継続する**。未紐付けであることを利用者に伝える
- ファイル添付は「ファイルは必須です」の表示が無ければ**添付済み**

### 6. 結果を報告する

以下を明示する。

- 作成した下書きのURL
- 既に申請済みだった場合は、その申請URLとステータス
- 紐付けできなかった稟議があれば、その検索条件
- 判定表に無く、判断を確認したい項目
- 読み取った金額と、実際に選んだ明細の金額

## うまくいかない時の切り分け

原因を段階で分けると、利用者に何を確認すべきかが決まる。

| 段階 | 症状 | 確認すること |
|---|---|---|
| PDF読み取り | 金額や請求書番号が取れない | PDFがテキストを含むか（画像のみのPDFはOCRが必要） |
| ログイン | バクラクの画面に入れない | 利用者がブラウザでログイン済みか。セッション切れでないか |
| 明細が0件 | 未申請明細の一覧が空 | **先に申請済タブを見る**。無ければカード明細がバクラクに未取り込み |
| 明細が一致しない | 一覧に該当行が無い | **先に申請済タブを見る**。無ければ読み取った金額・カード利用名・年月と、実際の明細を突き合わせる |
| 稟議が複数ヒット | 同名の稟議が年度違いで並ぶ | 請求書のサービス期間を含む年度か。請求額が利用可能額に収まるか |
| フォーム操作 | セレクタが見つからない | 画面構成が変わった可能性。`references/ui-flow.md` の記述を実画面と照合し、ズレていれば報告する |

判断に迷ったら、勝手に近い値を選ばず利用者に確認する。**金額や稟議を誤ると、経費申請として誤った内容が承認フローに乗る。**

## 判定表を更新する時

新しいベンダーに対応したら `references/vendors.local.md` に追記する。判定条件が既存の行と重複しないか確認する。重複すると、どちらに解決されるかが順序依存になる。

**`references/vendors.md` には具体的なベンダー名・番号・入力値を書かない。** このファイルは判定の考え方と書式のみを持つ。
